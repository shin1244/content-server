# content-server

Windows IOCP 기반 TCP 채팅 서버입니다.

처음에는 그냥 채팅만 되는 서버로 시작했고, 만들다 보니 친구, 인벤토리, 강화, 랭킹 같은 게임 서버 기능을 하나씩 붙이고 있습니다.
기능을 추가하면서 생기는 동시성 문제나 DB/Redis 처리 방식도 같이 고민해보고 있습니다.

* C++20 / Windows IOCP
* PostgreSQL, Redis
* Go 클라이언트 2종

  * 터미널 채팅 클라이언트
  * 부하 테스트용 봇

모든 입력은 채팅 한 줄로 받고, `/`로 시작하면 명령어로 처리합니다.

## 실행

환경변수 두 개가 필요합니다.

```bat
set SERVER_DB_DSN=postgresql://user:pw@host/db
set SERVER_REDIS_URL=tcp://127.0.0.1:6379
```

서버는 Visual Studio에서 빌드하고 `5050` 포트로 실행합니다.

클라이언트는 각각 다음처럼 실행합니다.

```bat
cd client && go build -o chat.exe . && chat.exe
cd bot    && go build -o bot.exe .  && bot.exe -n 100 -interval 1s
```

## 명령어

| 명령                              | 설명                 |
| ------------------------------- | ------------------ |
| `/n <이름>`                       | 로그인. 없으면 가입        |
| `(그냥 입력)`                       | 접속자 전체에게 브로드캐스트    |
| `/w <id> <내용>`                  | 귓속말                |
| `/f add <이름>`                   | 친구 요청              |
| `/f accept\|reject\|block <이름>` | 요청 수락 / 거절 / 차단    |
| `/f list`                       | 차단 / 받은 요청 / 친구 목록 |
| `/f <내용>`                       | 접속 중인 친구 전체에게 메시지  |
| `/i`                            | 골드, 총 전투력, 아이템 목록  |
| `/i enh <itemId>`               | 아이템 강화             |
| `/r`                            | 전투력 상위 20명         |
| `/r me`                         | 내 순위와 주변 순위        |

## 현재 되는 것

### 채팅

* 로그인 / 닉네임 설정
* 전체 채팅
* 귓속말
* 접속자 목록 동기화

  * 처음 접속하면 현재 명단을 한 번 전달
  * 이후에는 변경된 내용만 전달

### 친구

* 친구 요청 / 수락 / 거절 / 차단
* 친구 목록
* 친구 채팅
* 접속 중인 친구 캐시

### 인벤토리

채팅을 하면 소량의 보상을 받습니다.

* 골드 1~10
* 1/50 확률로 아이템 드랍
* 아이템 강화

### 랭킹

아이템 드랍이나 강화 성공 시 Redis ZSET을 갱신합니다.

서버가 시작할 때는 DB에서 전체 전투력을 읽어서 Redis 랭킹을 다시 만듭니다.

* `/r` : 상위 20명
* `/r me` : 내 순위 + 위아래 5명

### 클라이언트

* 터미널 채팅 클라이언트
* 부하 테스트용 봇 클라이언트

봇은 여러 개를 동시에 붙여놓고 세션 재사용이나 패킷 처리 같은 걸 확인하는 용도로 쓰고 있습니다.

## 다음에 할 것

* 아이템이 하나도 없는 유저는 랭킹에서 제외

  * 현재 `GetAllPower()`가 `items`와 `INNER JOIN`되어 있어서 이 부분은 의도한 동작인지 다시 정리할 예정
* 거래

  * 2인 상태머신 필요
  * 서로 다른 샤드에 있는 유저를 동시에 처리해야 해서 지금 구조에서 가장 큰 숙제
* 우편

  * 오프라인 유저에게도 전달할 수 있어야 함
* 귓속말 대상이 없을 때 명확한 에러 응답

특히 거래부터는 지금의 `sessionId % 8` 샤딩 모델만으로 깔끔하게 처리하기 어렵습니다.

## 구조

| 파일                                        | 역할                                     |
| ----------------------------------------- | -------------------------------------- |
| `NetworkCore`                             | IOCP 생성, AcceptEx, 워커 스레드 루프           |
| `Session`                                 | 세션별 recv/send, 링버퍼, 패킷 조립, IO 참조 카운트   |
| `SessionManager`                          | id/이름/userId 레지스트리, 세션 풀, 샤드 큐, 브로드캐스트 |
| `ShardServer`                             | 샤드별 큐 + Consumer 스레드 + DB 커넥션          |
| `Consumer`                                | 큐에서 명령을 꺼내 실제 채팅/친구/인벤토리 로직 처리         |
| `Database`                                | libpqxx 래퍼                             |
| `Ranking`                                 | Redis 래퍼. 순위 ZSET + 이름 HASH            |
| `Protocol`                                | 패킷 헤더와 `Packet` 정의                     |
| `MPMCQueue` / `RingBuffer` / `ObjectPool` | 큐 / 링버퍼 / 세션 풀                         |

전체적인 흐름은 단순합니다.

```text
클라이언트
    │
    ▼
IOCP 워커(N)
    │
    ▼
Session::OnRecv
    │
    │ sessionId % 8
    ▼
shardQueues_[0..7]
    │
    ▼
Shard Consumer(8)
    │
    ▼
Consumer::Handle
    ├── SessionManager
    ├── Database
    └── Ranking
```

패킷은 다음 형태입니다.

```text
[크기 2B][세션 id 2B][본문]
```

본문은 최대 256바이트입니다.

클라이언트는 세션 id를 `0`으로 보내고, 서버가 실제 세션 id로 덮어씁니다.
반대로 서버가 `0`을 넣어서 보내는 패킷은 시스템 메시지로 사용합니다.

## 샤딩

현재는 `sessionId % 8`로 샤드를 결정합니다.

한 유저가 보내는 패킷은 항상 같은 Consumer 스레드에서 처리되기 때문에, 유저 단위 상태는 별도의 락 없이 순서대로 처리할 수 있습니다.

```text
sessionId
    │
    └── % 8
         │
         ▼
    같은 Consumer
```

이 구조 덕분에 일반적인 채팅이나 인벤토리 명령은 꽤 단순하게 처리할 수 있습니다.

대신 문제가 되는 건 **두 유저를 동시에 건드리는 기능**입니다.

거래가 대표적입니다.
두 유저가 서로 다른 샤드에 있다면 한 Consumer 안에서 끝낼 수 없기 때문에, 지금의 "한 유저 = 한 Consumer"라는 전제를 깨지 않고 처리할 방법이 필요합니다.

거래를 다음 작업으로 잡은 이유도 이것 때문입니다.

## 강화와 DB 트랜잭션

강화는 애플리케이션에서 먼저 확인하고 나중에 차감하는 식으로 처리하지 않습니다.

예를 들어 골드 차감은 DB에서 조건까지 같이 검사합니다.

```sql
UPDATE users SET gold = gold - $2
WHERE user_id = $1 AND gold >= $2
RETURNING gold;
```

결과가 0행이면 골드가 부족한 것입니다.

아이템 쪽도 소유권을 `WHERE owner_id = $1`로 같이 검증합니다.

```text
골드 차감
   +
아이템 변경
   │
   ▼
하나의 트랜잭션
```

두 작업을 하나의 트랜잭션으로 묶었기 때문에 아이템 변경이 실패하면 골드 차감도 같이 롤백됩니다.

`owner_id` 검증은 DB 동시성 때문에 넣은 건 아닙니다.
클라이언트가 다른 사람의 `item_id`를 알고 요청하는 경우를 막기 위한 것입니다.

## 랭킹

랭킹 점수는 누적값이 아니라 **현재 전투력의 절대값**을 Redis에 넣습니다.

그래서 `ZINCRBY` 대신 `ZADD`를 사용합니다.

전투력 변경 시 어떤 갱신이 한 번 누락됐더라도, 다음 정상 갱신에서 현재 값으로 다시 덮어쓰면 됩니다.

```text
lb:power

userId → power
```

### 이름은 ZSET과 분리

처음에는 순위의 member를 이런 식으로 만들까도 생각했습니다.

```text
1024:홍길동
```

그런데 닉네임을 바꾸면 문제가 생깁니다.

```text
1024:홍길동
1024:김철수
```

같은 유저가 두 개의 member가 됩니다.
기존 닉네임을 알고 있으면 지울 수 있지만, 모르면 ZSCAN으로 찾아야 합니다.

그래서 userId와 닉네임을 아예 분리했습니다.

```text
lb:power
    userId → power

user:name
    userId → nickname
```

닉네임 변경은 HASH만 수정하면 됩니다.

```text
HSET user:name userId newName
```

이미 쌓여 있는 랭킹 데이터는 건드릴 필요가 없습니다.

### Redis 왕복 횟수

`Top()`에서 상위 20명을 가져올 때는

1. `ZREVRANGE`로 userId 20개 조회
2. `HMGET` 한 번으로 이름 20개 조회

이렇게 두 번 왕복합니다.

유저마다 `HGET`을 하면 총 21번 왕복하게 됩니다.

샤드 Consumer가 한 번에 한 패킷씩 처리하는 구조라서, 그동안 같은 샤드의 다른 요청이 전부 기다리게 됩니다.

이 경우 `for`문을 한 번 더 도는 비용은 거의 의미가 없고, Redis 왕복을 한 번 줄이는 게 훨씬 큽니다.

그래서 **조금 더 많은 로컬 연산을 하더라도 Redis 왕복 횟수를 줄이는 방향**으로 구현했습니다.

## DB / Redis 커넥션

`pqxx::connection`은 스레드 안전하지 않기 때문에 DB는 샤드마다 하나씩 둡니다.

```text
Shard 0 → Database → pqxx::connection
Shard 1 → Database → pqxx::connection
...
Shard 7 → Database → pqxx::connection
```

Redis 쪽은 `sw::redis::Redis`가 내부적으로 커넥션 풀을 사용하기 때문에 `Ranking` 하나를 두고 풀 크기를 샤드 수에 맞추는 방식으로 구성했습니다.

겉으로 보면 DB는 8개 객체, Redis는 1개 객체라 달라 보이지만, 의도는 결국 **Consumer 8개가 DB/Redis 작업을 서로 기다리지 않도록 하는 것**입니다.

## 트러블슈팅

### 랭킹 이름이 전부 `unknown`으로 나오던 문제

`GetAllPower()`의 SQL에 `user_name`을 추가하면서 결과 타입도 같이 수정해야 했는데, 결과를 받는 코드는 그대로 놔뒀습니다.

기존 코드는 이런 형태였습니다.

```cpp
RankEntry{row[0], row[1]}
```

`RankEntry`에 필드가 하나 더 생겨도 aggregate initialization 자체는 컴파일이 됐습니다.

결과적으로 세 번째 필드는 빈 문자열로 들어갔고, 그 값이 그대로 Redis에 저장됐습니다.

더 황당했던 건 `Ranking::SetName()`도 호출하는 곳이 없었다는 점입니다.

그래서 서버 재시작 → DB에서 랭킹 리빌드 → Redis에는 userId와 빈 이름만 저장 → 접속한 유저도 이름 갱신 안 됨

이 흐름으로 계속 `unknown`이 나왔습니다.

컴파일러가 잡아줄 거라고 생각했던 부분이 전혀 잡히지 않았던 케이스라 기억에 남았습니다.

### 세션 재사용하면서 이전 유저 정보가 남던 문제

더 위험했던 버그는 이쪽이었습니다.

`ObjectPool`에서 끊긴 세션 슬롯을 바로 재사용하고 있었는데, `Session::Init()`에서 `name_`과 `userId_`를 초기화하지 않았습니다.

그래서

```text
유저 A 접속
  ↓
name_ = A
userId_ = A
  ↓
연결 종료
  ↓
같은 Session 객체 재사용
  ↓
유저 B 접속
  ↓
name_ / userId_가 아직 A
```

가 되어버렸습니다.

처음에는 단순히 닉네임이 이상하게 찍히는 문제인 줄 알았는데, 로그인하지 않은 새 세션이 이전 유저의 계정으로 처리되면서 골드까지 남의 계정에 쌓일 수 있는 상태였습니다.

100개 정도 봇을 붙였다가 끊는 테스트를 반복하다가 다른 사람의 닉네임으로 채팅이 나가는 걸 보고 찾았습니다.

결국 `Session::Init()`에서 **재사용되는 모든 상태를 명시적으로 초기화**하도록 수정했습니다.

이런 종류의 버그 때문에 요즘은 기능을 하나 추가할 때 정상 동작만 보는 게 아니라,

* 연결 → 로그인 → 명령
* 연결 → 종료 → 같은 세션 재사용
* 여러 클라이언트 동시 요청
* DB/Redis 실패
* 잘못된 id를 클라이언트가 보내는 경우

까지 같이 보고 있습니다.

## 앞으로

지금 구조는 한 유저의 요청을 한 Consumer에서 순서대로 처리한다는 전제에서는 꽤 편합니다.

문제는 거래처럼 **여러 유저의 상태를 하나의 원자적인 작업으로 묶어야 하는 순간**부터입니다.

그래서 다음 목표는 단순히 거래 기능을 붙이는 것보다는, 현재 샤딩 구조를 유지하면서 cross-shard 작업을 어떻게 처리할지 먼저 정하는 것입니다.

그 이후에 우편까지 붙이면 게임 서버에서 자주 나오는 온라인/오프라인 상태, 단일 유저 작업/다중 유저 작업을 어느 정도 한 번씩은 다 다뤄볼 수 있을 것 같습니다.
